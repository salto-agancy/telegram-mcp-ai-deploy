# Облачный Telegram MCP для двух тестировщиков

**Сейчас** `src/oauth_proxy.py:build_proxy()` направляет все запросы в один backend с фиксированным bearer. `FixedClientOAuthProvider` получает клиента из файлов секретов, отключает DCR и сохраняет коды, токены доступа и обновления в `oauth-data:/data/oauth.db`. В `docker-compose.yml` сессии лежат в томе `telegram-sessions`, ACL подключён файлом. `scripts/telegram-login-web.sh` открывает портал через SSH.

## Изменения для пилота

- **Фасад.** В новом `src/cloud_oauth.py` переиспользуем `_secret()`, FastMCP и SQLite. Общий `/mcp` поддерживает обнаружение OAuth и DCR с выдачей секрета для `client_secret_post`. Обязательны PKCE S256 и точное совпадение разрешённого `redirect_uri`.
- **Чтение.** Новый `src/cloud_backend.py` запускается отдельно для каждого пользователя. Из инструментов `register_tools()` достаточно `get_messages` для истории и поиска по `query`. Сохраняем имя и формат ответа, добавляем курсор и ограничиваем размер страницы. Каждый вызов сверяет ID чата с ACL до чтения. Для любого чужого ID ответ одинаков. На этапе 2 используем вымышленные данные.
- **Подключение.** В новом `src/cloud_setup.py` используем `web_setup.create_session_client()` для входа по номеру, коду и 2FA. Код и пароль передаются Telegram без записи. Добавляем выбор одного чата, согласие, отключение и ограничения частоты входа и вызовов MCP.
- **Обновление.** Новый `docker-compose.cloud.yml` наследует ограничения контейнеров из основного Compose. В `scripts/auto_update.sh` отдельный `DEPLOY_CONFIG` выбирает проект пилота. Адаптируем `restart_account()`, `health()` и `roll_back()` для фасада и двух backend. После обновления из `release` проверяем их внутри сети, без архива. Используем существующие цели `Makefile`.

## Как запрос находит свой чат

Приглашение с ограниченным сроком связывает внутренний `user_id` с одним из двух контейнеров. После входа и согласия фасад привязывает код OAuth к клиенту и гранту пользователя. На каждом запросе по действующему токену проверяет грант, затем по `user_id` выбирает адрес backend и его внутренний bearer из серверной конфигурации. Без токена и после отзыва возвращает HTTP 401. Обновление токена сохраняет привязку, отзыв закрывает все токены гранта.

В проекте `telegram-mcp-cloud` свой том `oauth-data:/data/oauth.db` для клиентов DCR, хешей секретов и токенов, кодов OAuth, грантов и привязок. Внутренние bearer подключаются файлами секретов пилота. У каждого backend свой постоянный том с сессией Telethon и ACL. При обновлении и откате тома сохраняются. При отключении сначала отзывается доступ, затем удаляются сессия, ACL и состояние пользователя.

## Риски и проверки владельца

1. На iPhone проверить адрес возврата Perplexity, получение кода в Telegram и чтение после закрытия окна OAuth за целевые 1–3 минуты. Если вход невозможен, Bot API позволит проверить только маршрутизацию и ACL.
2. Старый портал журналирует `phone_code_hash`. Для пилота нужны отдельные обработчики и журналы только со статусами, счётчиками, версией и обезличенными ошибками.
3. Администратор VPS имеет доступ к сессиям. Для теста нужны два чата с вымышленными сообщениями.
4. Перед развёртыванием проверить ресурсы VPS и свободный маршрут существующего туннеля к фасаду. Оба backend доступны только внутри проекта.

## Этап 2. Рабочая схема на вымышленных данных

- Фасад запускается через `python -m src.cloud_oauth`. Ему нужны `PUBLIC_BASE_URL` (HTTPS), точные адреса возврата в `MCP_OAUTH_REDIRECT_URIS` через запятую, путь `OAUTH_DB_PATH` и закрытый файл `CLOUD_ROUTES_FILE`. В нём JSON-объект по внутреннему `user_id` с полями `url` (внутренний адрес `/v1/mcp`), `bearer` и `invite_sha256` (SHA-256 случайного приглашения).
- Каждый `python -m src.cloud_backend` получает свой `FIXTURE_CHAT_ID` и `CLOUD_BACKEND_BEARER_FILE`. Порт каждого процесса задаёт `BIND_PORT`, адрес по умолчанию — loopback. Один `get_messages` читает выбранный чат, ищет по `query` и возвращает `next_cursor` для следующей страницы.
- Приглашение вводится в форму. Обратно в клиент уходят одноразовый код (120 секунд) и переданный клиентом `state`. Токен доступа действует час. Обновление заменяет оба токена, отзыв по любому выданному токену закрывает весь грант. Журнал содержит только код HTTP-ответа.

## Этап 3. Подключение Telegram

Для каждого пользователя в `CLOUD_ROUTES_FILE` задаются `expires` (целое число секунд Unix UTC) и `telegram: true`. До истечения срока приглашением можно пользоваться повторно. Новый грант отзывает предыдущие гранты пользователя. Фасад ограничивает запросы к регистрации, авторизации, выдаче токенов, подключению и MCP по IP в памяти процесса.

Каждый боевой backend получает свой `CLOUD_SESSION_PATH`, `TELEGRAM_API_ID` и `TELEGRAM_API_HASH_FILE`. После входа по номеру, коду и при необходимости паролю выбери один тестовый чат и подтверди чтение. Сессия и ACL сохраняются одним закрытым файлом в томе пользователя. Для отключения открой `/setup` в том же браузере, где выдан доступ. Сервер отзывает грант и удаляет файл. QR-вход с одного iPhone остаётся непроверенным.
