# Облачный Telegram MCP для двух тестировщиков

**Сейчас** `src/oauth_proxy.py:build_proxy()` направляет все запросы в один backend с фиксированным bearer. `FixedClientOAuthProvider` получает клиента из файлов секретов, отключает DCR и сохраняет коды, токены доступа и обновления в `oauth-data:/data/oauth.db`. В `docker-compose.yml` сессии лежат в томе `telegram-sessions`, ACL подключён файлом. `scripts/telegram-login-web.sh` открывает портал через SSH.

## Изменения для пилота

- **Фасад.** В новом `src/cloud_oauth.py` переиспользуем `_secret()`, FastMCP и SQLite. Общий `/mcp` поддерживает обнаружение OAuth и DCR с выдачей секрета для `client_secret_post`. Обязательны PKCE S256 и точное совпадение разрешённого `redirect_uri`.
- **Чтение.** Новый `src/cloud_backend.py` запускается отдельно для каждого пользователя. Из инструментов `register_tools()` достаточно `get_messages` для истории и поиска по `query`. Сохраняем имя и формат ответа, добавляем курсор и ограничиваем размер страницы. Каждый вызов сверяет ID чата с ACL до чтения. Для любого чужого ID ответ одинаков. На этапе 2 используем вымышленные данные.
- **Подключение.** В новом `src/cloud_setup.py` используем `web_setup.create_session_client()` для входа по номеру, коду и 2FA. Код и пароль передаются Telegram без записи. Добавляем выбор одного чата, согласие, отключение и ограничения частоты входа и вызовов MCP.
- **Обновление.** Новый `docker-compose.cloud.yml` наследует ограничения контейнеров из основного Compose. В `scripts/auto_update.sh` отдельный `DEPLOY_CONFIG` выбирает проект пилота. Адаптируем `restart_account()`, `health()` и `roll_back()` для фасада и двух backend. После обновления из `release` проверяем их внутри сети, без архива. Используем существующие цели `Makefile`.

## Как запрос находит свой чат

Приглашение с ограниченным сроком связывает внутренний `user_id` с одним из двух контейнеров. После входа и согласия фасад привязывает код OAuth к клиенту и гранту пользователя. На каждом запросе по действующему токену проверяет грант, затем по `user_id` выбирает адрес backend и его внутренний bearer из серверной конфигурации. Без токена и после отзыва возвращает HTTP 401. Обновление токена сохраняет привязку, отзыв закрывает все токены гранта.

В проекте `telegram-mcp-cloud` свой том `oauth-data:/data/oauth.db` для клиентов DCR, хешей секретов и токенов, кодов OAuth, грантов и привязок. Внутренние bearer подключаются файлами секретов пилота. У каждого backend свой постоянный том с сессией Telethon и ACL. При обновлении и откате тома сохраняются. При отключении сначала отзывается доступ, затем удаляются сессия, ACL и состояние пользователя.

## Риски и проверки владельца

1. На iPhone проверить адрес возврата Perplexity, получение кода в Telegram и чтение после закрытия окна OAuth за целевые 1–3 минуты. Если вход невозможен, Bot API позволит проверить только маршрутизацию и ACL.
2. Старый портал журналирует `phone_code_hash`. Для пилота нужны отдельные обработчики и журналы только со статусами, счётчиками, версией и обезличенными ошибками.
3. Администратор VPS имеет доступ к сессиям. Для теста нужны два чата с вымышленными сообщениями.
4. Перед развёртыванием проверить ресурсы VPS и свободный маршрут существующего туннеля к фасаду. Оба backend доступны только внутри проекта.

## Этап 2. Рабочая схема на вымышленных данных

- Фасад запускается через `python -m src.cloud_oauth`. Ему нужны `PUBLIC_BASE_URL` (HTTPS), точные адреса возврата в `MCP_OAUTH_REDIRECT_URIS` через запятую, путь `OAUTH_DB_PATH` и закрытый файл `CLOUD_ROUTES_FILE`. В нём JSON-объект по внутреннему `user_id` с полями `url` (внутренний адрес `/v1/mcp`), `bearer` и `invite_sha256` (SHA-256 случайного приглашения).
- Каждый `python -m src.cloud_backend` получает свой `FIXTURE_CHAT_ID` и `CLOUD_BACKEND_BEARER_FILE`. Порт каждого процесса задаёт `BIND_PORT`, адрес по умолчанию — loopback. Один `get_messages` читает выбранный чат, ищет по `query` и возвращает `next_cursor` для следующей страницы.
- Приглашение вводится в форму. Обратно в клиент уходят одноразовый код (120 секунд) и переданный клиентом `state`. Токен доступа действует час. Обновление заменяет оба токена, отзыв по любому выданному токену закрывает весь грант. Журнал содержит только код HTTP-ответа.

## Этап 3. Подключение Telegram

Для каждого пользователя в `CLOUD_ROUTES_FILE` задаются `expires` (целое число секунд Unix UTC) и `telegram: true`. До истечения срока приглашением можно пользоваться повторно. Новый грант отзывает предыдущие гранты пользователя. Фасад ограничивает запросы к регистрации, авторизации, выдаче токенов, подключению и MCP по IP в памяти процесса.

Каждый боевой backend получает свой `CLOUD_SESSION_PATH`, `TELEGRAM_API_ID` и `TELEGRAM_API_HASH_FILE`. После входа по номеру, коду и при необходимости паролю выбери один тестовый чат и подтверди чтение. Сессия и ACL сохраняются одним закрытым файлом в томе пользователя. Для отключения открой `/setup` в том же браузере, где выдан доступ. Сервер отзывает грант и удаляет файл. QR-вход с одного iPhone остаётся непроверенным.

## Этап 4. Изолированные обновления

Проект `telegram-mcp-cloud` использует три постоянных тома и отдельные файлы секретов. У каждого backend отдельные сети для доступа фасада и выхода в Telegram. Опубликован только частный порт фасада. Фасад принимает `CF-Connecting-IP` для ограничений частоты только от заданного `CLOUD_TRUSTED_PROXY_IP`.

После успешных проверок на том же коммите отдельный процесс CI продвигает ветку `release-cloud`. `scripts/cloud_auto_update.sh` собирает образ с тегом коммита, последовательно проверяет оба backend и фасад. При ошибке возвращает предыдущий образ по сохранённому хешу. Контейнеры пересоздаются с прежними томами. Обновление по таймеру использует свою блокировку и отдельный файл конфигурации.

## Этап 5. План развёртывания и отката

Владелец подтверждает коммит и окно работ по действующему процессу, прежде чем запускать команды на VPS. Сначала сверить ресурсы и свободный адрес origin. Команды предварительной проверки читают состояние:

```bash
uptime
free -h
df -h /opt /var/lib/docker
docker system df
docker compose ls
sudo ss -ltnp
ip -br address
```

1. Убедиться, что `release-cloud` указывает на согласованный коммит и проверка `Cloud pilot release` зелёная. Выбрать отдельное имя узла в существующем домене и новый частный origin-порт. Проверить, что такого имени и правила ещё нет в существующем Cloudflare Tunnel. Убедиться, что каждый действующий экземпляр коннектора этого туннеля видит новый origin. Сохранить перечень действующих правил и контрольные ответы рабочего и личного MCP.
2. На VPS выделить каталоги `/opt/telegram-mcp-cloud`, `/etc/telegram-mcp-cloud` и `/var/lib/telegram-mcp-cloud`. В отдельный каталог клонировать ветку `release-cloud`, проверить её хеш через `git rev-parse HEAD`. Подготовить `/etc/telegram-mcp-cloud/pilot.env` с переменными из `docker-compose.cloud.yml`. `CLOUD_BIND_IP` указывает частный адрес, доступный коннектору. `CLOUD_TRUSTED_PROXY_IP` указывает один подтверждённый адрес TCP-источника, который видит фасад после NAT Docker. Для коннектора на хосте сначала проверить loopback. Для контейнерного коннектора проверить достижимость по уже доступному ему адресу. Допускать к origin только коннектор, с учётом фильтрации опубликованных Docker-портов. Если адрес источника общий с другими процессами или сеть недоступна, остановиться до публикации маршрута.
3. В каталоге `CLOUD_SECRET_DIR` подготовить файлы `first-bearer`, `second-bearer`, `api-hash` и `routes.json`. Сгенерировать два разных внутренних ключа и два случайных приглашения (по 32 байта). В `routes.json` записать хеши приглашений, согласованный срок `expires`, `telegram: true`, ключи и внутренние адреса `http://cloud-first:8000/v1/mcp` и `http://cloud-second:8000/v1/mcp`. Файлы секретов доступны только назначенному UID/GID образа и администратору. В `/etc/telegram-mcp-cloud/update.env` задать `CLOUD_APP_DIR=/opt/telegram-mcp-cloud`, `CLOUD_ENV_FILE=/etc/telegram-mcp-cloud/pilot.env` и `CLOUD_STATE_DIR=/var/lib/telegram-mcp-cloud`. Сверить точный адрес возврата Perplexity с `CLOUD_REDIRECT_URIS`.
4. Запустить только проект пилота и проверить три статуса. Запуск производится по согласованному хешу ветки релиза:

   ```bash
   cd /opt/telegram-mcp-cloud
   sudo env CLOUD_DEPLOY_CONFIG=/etc/telegram-mcp-cloud/update.env ./scripts/cloud_auto_update.sh
   sudo env CLOUD_IMAGE_TAG="$(git rev-parse HEAD)" docker compose -p telegram-mcp-cloud \
     --env-file /etc/telegram-mcp-cloud/pilot.env -f docker-compose.cloud.yml ps
   ```

5. Добавить отдельное правило имени узла в существующий туннель. Направить все пути этого имени на частный origin фасада. Проверить `/.well-known/oauth-protected-resource/mcp` и `/.well-known/oauth-authorization-server` с ответом 200, `POST /mcp` без токена с ответом 401, а также обычный OAuth-запрос через туннель. Проверить, что IP-разделение работает через туннель, а прямой заход с поддельным `CF-Connecting-IP` отклоняется. Сверить прежние контрольные ответы рабочего и личного MCP. Затем по согласованию поставить отдельные systemd-файлы пилота, выполнить `systemctl daemon-reload` и включить `telegram-mcp-cloud-update.timer`.

Проверки после добавления маршрута. Задай `PILOT_URL` с адресом пилота без завершающего слеша:

```bash
curl --fail --silent --output /dev/null --write-out '%{http_code}\n' \
  "$PILOT_URL/.well-known/oauth-authorization-server"
curl --fail --silent --output /dev/null --write-out '%{http_code}\n' \
  "$PILOT_URL/.well-known/oauth-protected-resource/mcp"
curl --silent --output /dev/null --write-out '%{http_code}\n' -X POST "$PILOT_URL/mcp"
```

Из среды каждого коннектора выполни `curl --fail --silent --output /dev/null "$PILOT_ORIGIN/.well-known/oauth-authorization-server"`, где `PILOT_ORIGIN` — частный HTTP-адрес с портом. Если в образе коннектора отсутствует `curl`, используй проверку доступности origin в панели туннеля. Сохрани только коды ответов.

### Откат

Сначала отключить `telegram-mcp-cloud-update.timer` и убедиться, что обновление завершилось. При первом развёртывании убрать правило хоста пилота в туннеле, затем выполнить `docker compose -p telegram-mcp-cloud --env-file /etc/telegram-mcp-cloud/pilot.env -f docker-compose.cloud.yml stop` с `CLOUD_IMAGE_TAG` текущего коммита. При откате обновления взять последний исправный хеш и его сохранённый образ, переключить отдельный checkout на этот хеш и поднять по очереди `cloud-first`, `cloud-second`, `cloud-oauth` командой `up -d --no-deps --no-build --wait --wait-timeout 100 SERVICE` с тем же Compose-файлом и `CLOUD_IMAGE_TAG` исправного коммита. Записать исправный хеш в `/var/lib/telegram-mcp-cloud/deployed` после проверки состояния. Сохранить тома и секреты. Автообновление возобновить после появления исправленного релиза. Повторить контрольные запросы к пилоту и обоим действующим MCP.

## Инструкция для iPhone

1. Открой настройки подключений MCP в Perplexity и добавь общий URL пилота с путём `/mcp`.
2. В окне OAuth введи своё приглашение и номер Telegram.
3. Открой Telegram на том же iPhone, возьми код и вернись в окно OAuth. Если форма запросит пароль двухэтапной проверки, введи его.
4. Выбери свой тестовый чат с вымышленными сообщениями и нажми «Разрешить чтение». Дождись возврата в Perplexity.
5. После закрытия окна попроси Perplexity найти контрольную фразу в выбранном чате.
6. Повтори запрос после перезапуска или согласованного обновления пилота. Владелец отдельно проверяет с учётной записи второго участника отказ для известного ID первого чата.
7. Для отключения открой `/setup` на адресе пилота в том же браузере, где выдан доступ, и нажми «Отключить».

### Адреса возврата Perplexity

В `pilot.env` задай `CLOUD_REDIRECT_URIS=https://www.perplexity.ai/rest/connections/oauth_callback,https://enterprise.perplexity.ai/rest/connections/oauth_callback`. Оба адреса закреплены для публичного клиента `https://www.perplexity.ai/.well-known/mcp-client.json`. Фасад сверяет их с настройкой, требует PKCE S256 и использует сохранённые значения без исходящих запросов при авторизации. При DCR по-прежнему выдаётся секрет.

## Часть B. Развёртывание и откат

Сохраняй DNS-записи пилота при любом откате. Если нужно снять публикацию, откати только правило туннеля.

1. После отдельного согласования закрепи коммит с зелёным CI. Сохрани хеш и образ части A, исходный `docker-compose.cloud.yml`, её `pilot.env` и резервную копию маршрута туннеля. Для части B подготовь выделенный checkout и свой `community.env` с тем же публичным адресом и портом пилота. Возьми подтверждённый TCP-адрес origin из части A.
2. В BotFather настрой Main Mini App на `/app` публичного адреса. Задай `CLOUD_BOT_USERNAME` без `@`, `OWNER_TELEGRAM_ID` и `CLOUD_SLOTS` (по умолчанию 10). Добавь `bot-token` и `api-hash` как файлы секретов генератора, доступные UID/GID образа. Бот и фасад используют токен для Bot API и проверки подписи Mini App.
3. Из checkout с согласованным коммитом, с `CLOUD_SLOTS`, `CLOUD_UID` и `CLOUD_GID` из настроек среды, выполни `uv run --frozen python -m src.cloud_render "$COMMUNITY_COMPOSE" "$CLOUD_SECRET_DIR"`. Генератор сохраняет закрытые файлы с ключами маршрутов и создаёт по одному контейнеру и тому на слот. Для увеличения числа мест измени `CLOUD_SLOTS`, повтори генерацию и запуск.
4. Задай `CLOUD_IMAGE_TAG` равным согласованному хешу. Проверь конфигурацию командой `docker compose -p telegram-mcp-cloud --env-file "$COMMUNITY_ENV" -f "$COMMUNITY_COMPOSE" config --quiet`. Собери образ командой `build cloud-oauth`, затем тем же Compose запусти `up -d --no-build --wait --remove-orphans`. Проверь фасад, бота и состояние контейнеров. Подтверди HTTP 200 для обнаружения OAuth и HTTP 401 для `/mcp` без токена. Проверь личный и рабочий MCP по контрольным запросам части A.
5. При откате верни запуск части A её Compose-файлом и сохранённым `CLOUD_IMAGE_TAG` командой `up -d --no-build --wait --remove-orphans`. Не добавляй `--volumes`: часть B использует свои тома и SQLite, а состояния частей A и B не мигрируют. Повтори все контрольные запросы после отката. Если менялось правило туннеля, сначала верни сохранённый конфиг и проверь его перед перезапуском.

### Вход в пилот

Подключение новых аккаунтов через номер, код Telegram и пароль двухэтапной проверки отключено. Если Telegram прислал уведомление о входе во время предыдущей попытки, проверь устройство и время в «Настройки → Устройства». Там же можно завершить конкретный сеанс.

Для ранее подключённых аккаунтов выбор чатов и управление доступом остаются в Mini App. После подтверждения запроса вернись в исходное окно ИИ для завершения OAuth.

Приглашённый участник может добавить MCP URL в Perplexity и подтвердить подключение через Telegram до привязки аккаунта. Окно OAuth ждёт 10 минут. Пока нет сессии и разрешённых чатов, список чатов пуст и чтение по любому ID закрыто. Если запрос истёк, начни подключение снова в Perplexity. Место в пилоте сохраняется.

Трёхзначное число на экранах OAuth и Mini App служит только для сверки одного запроса. Его не нужно вводить. Это не код входа Telegram. Приглашение одноразовое: после закрепления слота участник открывает бота через `/start`, новая ссылка нужна другому участнику или после «Удалить всё».
